# Ghidra runtime and dataset feasibility

Research for [ticket #2](https://github.com/hamedzurat/esperware/issues/2), under [map #1](https://github.com/hamedzurat/esperware/issues/1). Verified 2026-11-09. This is API/source research, not a tested runtime prototype. No implementation, binary patching, student selection, or evaluation protocol is proposed here.

## Findings and scope

A persistent runtime is feasible through official Ghidra APIs: retain the project, Program consumer, and decompiler in a long-lived process. This does **not** establish that any particular third-party MCP already satisfies the requested contract. Ghidra-100K is a text-pair release, not a set of replayable Ghidra projects. Existing text can inform proposed edits; only calls actually executed against the corresponding live program establish their results.

## Runtime facts

The [official latest-release API](https://api.github.com/repos/NationalSecurityAgency/ghidra/releases/latest) returned `Ghidra_12.2_build`. The [12.2 release](https://github.com/NationalSecurityAgency/ghidra/releases/tag/Ghidra_12.2_build) is a concrete candidate to pin, not a compatibility guarantee for extensions. The current [official PyGhidra README](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Features/PyGhidra/src/main/py/README.md) documents Ghidra 12.0+ for its current API, CPython through JPype, headless `start`, project opening, and explicit program consumption/release. Do not copy these newer helpers into an older installation without checking its bundled documentation. Ghidra stubs are version-specific. Pin Ghidra distribution, bundled Python package, JVM requirements from that distribution, extensions, language/compiler IDs, analyzer settings and decompiler options together.

| Runtime | Persistence and access | Constraint |
| --- | --- | --- |
| Long-lived CPython/PyGhidra | `start`, `open_project`, `consume_program` retain Java objects and the program consumer | Scope resource cleanup to the session, not each MCP request; release consumer and close project on shutdown |
| Java Ghidra application/plugin | Direct Java API; GUI plugin can operate on the GUI-owned program | Coordinate with GUI transactions and tool task scheduling; GUI selection is not a durable program identifier |
| `analyzeHeadless` batch scripts | Official import/process/script automation | A separate invocation per tool call does not preserve an in-memory session; useful for preparation, not by itself the requested live service |

Sources: [PyGhidra](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Features/PyGhidra/src/main/py/README.md), [headless documentation source](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/RuntimeScripts/Common/support/analyzeHeadlessREADME.html), [Ghidra project API](https://ghidra.re/ghidra_docs/api/ghidra/base/project/GhidraProject.html). These are integration building blocks, not an official MCP wire protocol.

[DecompInterface](https://ghidra.re/ghidra_docs/api/ghidra/app/decompiler/DecompInterface.html) explicitly supports repeated decompilations of one open program. It retains initialization and respawns its native decompiler after a crash. `openProgram` returns success; repeated calls restart the process. Check `DecompileResults.decompileCompleted()` and `getErrorMessage()` rather than assuming nonempty text means success. Timeouts and cancellation are failures to obtain an answer, not proof that an edit is invalid. `flushCache()` clears cached function/symbol information; `resetDecompiler()` resets the native process. A new decompilation must replace old HighFunction/token/variable handles after edits.

[DomainObject](https://ghidra.re/ghidra_docs/api/ghidra/framework/model/DomainObject.html) requires transactions for changes. Concurrent subtransactions are coupled: failure to commit one rolls back concurrent changes. It exposes changeability, exclusive access, modification number, save, undo/redo capability and consumer lifecycle. Consequently transaction nesting is **not request isolation**. Undo is a stack of recent transactions, can be cleared, and is not an archival trajectory or a promised durable undo history after reopening. Save the program explicitly and verify save errors; reopening retrieves persisted database state, not Python handles, decompiler cache, or request history. Do not assume project upgrades remain backward readable.

### Inspection and edit surface

The official [Function API](https://ghidra.re/ghidra_docs/api/ghidra/program/model/listing/Function.html) provides entry point/body, calling/called functions, parameters, locals, return type, signature, calling convention, and `updateFunction`/`replaceParameters`. It warns that deprecated `addParameter` can mishandle auto-parameters. Signature edits must account for storage, calling convention and auto-parameters; a successful type assignment is not evidence of semantic correctness.

[ReferenceManager](https://ghidra.re/ghidra_docs/api/ghidra/program/model/symbol/ReferenceManager.html) supplies references to/from addresses. [DataTypeManager](https://ghidra.re/ghidra_docs/api/ghidra/program/model/data/DataTypeManager.html) owns database types. [HighFunctionDBUtil](https://ghidra.re/ghidra_docs/api/ghidra/program/model/pcode/HighFunctionDBUtil.html) bridges decompiler variables/prototypes to database edits. [Symbol](https://ghidra.re/ghidra_docs/api/ghidra/program/model/symbol/Symbol.html) supplies ID, address, namespace, name, source and `isDeleted`; rename can throw duplicate-name/invalid-input errors. Known callers are analysis-derived; indirect calls need not be resolved.

Recommendation (not an approved contract): serialize mutation and decompilation per program, including GUI changes and background analysis. Check expected revision before mutation; resolve IDs anew; validate program ownership, symbol existence, expected kind and address; execute one transaction; rollback on failure; read back persisted fields; invalidate decompiler data and redecompile before selecting another action. Record both API outcome and decompilation outcome. A stale revision must prompt inspection, not silently retarget an edit.

Example sequence, illustrative only: inspect function → propose rename with expected program revision and symbol ID → transaction/rename/commit → flush cache → decompile → record actual text and diagnostics. For an experimental signature, retain prior signature, storage and provenance and restore deliberately if rejected. A later global undo may undo unrelated GUI work. For durable recovery, use saved baseline copies/checkpoints and a harness history.

Recommendation: identity should include harness project/program identity plus database symbol ID and address-space-qualified entry point; names are mutable. IDs are not universal across independently imported binaries, deleted/recreated symbols, or rebuilt projects. Retain binary hash and analysis manifest for provenance. Decompiler locals require revision-scoped handles, not C token names as permanent IDs.

## Dataset evidence

### Ghidra-100K: verified identity

The actual release is [LLM4Binary/decompile-ghidra-100k](https://huggingface.co/datasets/LLM4Binary/decompile-ghidra-100k). The [live artifact API](https://huggingface.co/api/datasets/LLM4Binary/decompile-ghidra-100k) returned revision `9f9c6a839b4df455835049d1932baa896e05486f`, README, attributes and one `data/train-00000-of-00001.parquet` file. Its card declares MIT and exactly 100,000 training entries with string columns `instruction` and `output`. It describes Ghidra pseudocode/source pairs and points to [LLM4Decompile training instructions](https://github.com/albertan017/LLM4Decompile/tree/main/train). The author's [release history](https://github.com/albertan017/LLM4Decompile) says 25k per optimization level; its project describes C, Linux x86-64 and GCC O0–O3. Those project-level statements do not supply row-level compiler manifests.

The published schema has no binary bytes, project, source repository revision, function address, compiler command, Ghidra version, or alignment key. The listed release contains no binary/project artifacts. Source-function text is not necessarily a complete translation unit with original headers/build dependencies. Pairing is claimed by the publisher; this investigation has not independently validated every pair or its source licensing. The MIT card declaration does not independently establish provenance of every embedded source snippet. This is the 2024 text release; do not confuse it with the separate 2025 Decompile-Bench announcement or infer million-scale binary artifacts from that announcement.

### Decompile-Bench: artifact and provenance audit

The first-party [LLM4Decompile release notes at repository revision `85b364b`](https://github.com/albertan017/LLM4Decompile/tree/85b364bf093eb2ee4f3687cfe38a203fca89f23e/decompile-bench) identify C and C++ and describe a compile-trace-filter pipeline. Its README lists four training columns: demangled `name`, source `code`, `asm`, and source `file`. The pinned [Hugging Face table snapshot `4b708c2`](https://huggingface.co/datasets/LLM4Binary/decompile-bench/tree/4b708c2211cd7d4af403675db56322aa4ed7050c) has 2,233,092 rows in 17 Arrow shards (8.46 GB per dataset metadata); the displayed sample is source and assembly with a repository-relative source path. Thus the primary training table is not pseudocode and does not itself contain binary bytes or a Ghidra project. The pinned [dataset card](https://huggingface.co/datasets/LLM4Binary/decompile-bench/blob/4b708c2211cd7d4af403675db56322aa4ed7050c/README.md) declares CC0-1.0 for that dataset.

The publisher separately releases [Decompile-Bench binaries](https://huggingface.co/datasets/LLM4Binary/decompile-bench-bins/tree/173b32f8e963daabb0807585f4f3e202dfb0dcc7), an observed 140 GB archive split into 2 GB multipart files. Its pinned card says these are the benchmark binaries; the first-party dataset README says they include debugging information. In a first-party GitHub answer, the owner describes them as unstripped and full-debug-info, and cautions that the expanded archive is about 500 GB ([issue #51](https://github.com/albertan017/LLM4Decompile/issues/51#issuecomment-2994742354)). Inference: these downloadable binary artifacts should support direct import into a newly created Ghidra project; I did not extract or import one, so this is not runtime-verified. They are not Ghidra project databases. The archive card and LICENSE declare MIT, while the curated text table declares CC0. Those dataset-level declarations do not establish the individual upstream source repositories' rights; retain and review original project licenses before reuse.

The [raw companion release](https://huggingface.co/datasets/LLM4Binary/decompile-bench-raw/tree/f75607ebd01926530561cd220c3ab858489b4c1f) is a 30 GB zip according to its file page and advertises roughly 110 million rows. Its displayed schema includes source, assembly, source `path`, an `opt` value, and build/binary path-like provenance; one actual sample shows `build_O0` and a `.asm_src.json` artifact. It is declared MIT at the dataset level. The [raw-address companion](https://huggingface.co/datasets/LLM4Binary/decompile-bench-raw-address/tree/9bf845ef57f3e8dff45261a88ed3b93554502f20) is another separately hosted archive, also declared MIT. The [makefile companion](https://huggingface.co/datasets/LLM4Binary/decompile-bench-makefile/tree/5ff684062b433ad348e19e7360f9411c3bc9c904) declares CC0 and describes 643K function pairs from 2,600 projects, but its sample schema is still `name`, `code`, `asm`, and `file`.

**Alignment result:** the publisher claims the curated pairs are derived from compiled projects, and it publishes related binary, raw-row, and raw-address artifacts. Names, source paths, optimization labels, debug information, and address companions make matching plausible. I did not download and unpack the 140 GB binary archive, audit all 2.2M row mappings, or find a pinned source repository commit plus complete compiler/link flags/build manifest per curated row. Consequently exact sample-to-binary identity, deterministic rebuild equivalence, coverage of each curated row in the binary bundle, and original licensing at each source path remain **unverified**. The README's advertised alignment is publisher evidence, not an independent per-row validation. The available artifacts can support selected direct-import experiments after a row is matched and rights reviewed; text rows alone cannot establish Ghidra output or replay an executed MCP episode.

| Dataset | Language and license | Build, provenance, and alignment | Trajectory use |
| --- | --- | --- | --- |
| Decompile-Bench curated table | C/C++; CC0 declaration on the table snapshot; upstream project licenses still apply | 2.23M source/assembly rows with source paths; no binary bytes, project, full build manifest, or Ghidra output in the table | Proposal/reference material only until matched to a binary; then candidate for direct import and actual tool execution |
| Decompile-Bench binaries | C/C++ benchmark artifacts; MIT declaration on archive, not a blanket grant for embedded upstream code | Separate 140 GB multipart archive, unstripped/debug-info per publisher; exact row coverage, mapping and reproducible build settings were not independently checked | Actual binaries can be imported into a new Ghidra project; not ready-made projects or proven trajectory histories |
| Decompile-Bench raw / raw-address | C/C++; MIT dataset declarations; per-origin license audit still needed | Large raw archives expose source, assembly, paths and optimization/build path fields; address data is separately packaged; no completed cross-release hash audit | Possible discovery/matching inputs, not proof of a specific Ghidra decompilation |
| Decompile-Bench makefile companion | C/C++; CC0 declaration plus upstream rights | 643K rows from makefile projects; same source/assembly/path style, no project or binaries documented in the sample schema | Rebuild candidates only; build reproducibility must be established per project |

The [versioned Decompile-Bench paper](https://papers.nips.cc/paper_files/paper/2025/file/079cf13ae174c31f148207d94d213bdc-Paper-Datasets_and_Benchmarks_Track.pdf) describes filtering for permissively licensed repositories and compiling C/C++ at four optimization levels. This is useful provenance context, not proof of the license or compiler flags for any individual row. The current main release card and binaries license metadata differ (CC0 table vs MIT binaries/raw), so never infer one asset's license from another. In contrast, ExeBench's pinned [repository README](https://github.com/jordiae/exebench/blob/8b47d483c2e39ea40a304fbaac46e41a1a14272f/README.md) explicitly says the C snippets retain their original GitHub licenses (recorded in metadata) and only ExeBench-added I/O examples/boilerplate are MIT. It provides dependency/context and assembly data for some compilable subsets, but no source-matched ready Ghidra binary/project release was verified. Its row-level source and assembly are therefore rebuild inputs, not source-to-Ghidra replay evidence. AnghaBench's missing-license issue remains open, so its use is not cleared by its open-source origin.

No candidate above supplies the requested executed tool trajectories out of the box. Dataset license declarations, compilability and alignment are separate questions. Inlining, optimization, synthesized stubs and removed context can break one-source-function/one-Ghidra-function assumptions.

## Recommendations and remaining verification

Use official persistent APIs as the runtime foundation, with a serialized owner and explicit session lifecycle. Prefer automated generation from owned buildable projects for the initial corpus; use existing text pairs as proposal context only until exact corresponding artifacts are established. These are recommendations for later contract decisions, not human choices resolved by this ticket.

For every replayable episode retain source revision/license, dependencies, compiler version/flags/target, binary hash and bytes, source-to-address provenance, Ghidra version/language/compiler/analyzer settings, baseline project/checkpoint and actual calls/results. Source-aware teacher selects a call using source plus current pseudocode; harness executes that exact call on the persistent project and returns real results before the next choice. Keep oracle source hidden from student evidence. Preserve input binary hash and exclude memory/byte patch operations entirely.

## What this resolves and what remains open

The evidence answers the research question: official Ghidra APIs support a live program/decompiler in a long-lived process, and the cited datasets range from text-only pairs to separate binaries, with no dataset providing already-executed episodes through this project's future MCP contract. Dataset gaps do **not** block the design of that MCP contract: it can define stable session/program identity, required persistence and mutation behavior, actual-result reporting, and provenance fields without committing to any external dataset. Whether a selected Ghidra build/extension meets those requirements still needs a small runtime acceptance probe before implementation decisions are treated as validated. Dataset gaps do block claiming that these external rows are already replayable or cleared for ingestion; a chosen Decompile-Bench row needs a binary match, project-license review and actual import/decompile check, while owned buildable projects give the strongest route to reproducible episodes.

Unresolved evidence is explicit, not unfinished reading: no Ghidra runtime was installed for save/reopen or concurrency experiments; the Decompile-Bench binary archive and cross-release row/address mappings were not fully downloaded/audited; upstream source rights were not resolved row-by-row; and ExeBench alignment was not tested against original binaries. These findings do not select a student model, training set, evaluation metric, or human contract choice. They define acceptance evidence needed later.
